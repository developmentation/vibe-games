CI/CD pipeline requirements

Every TI-managed application must have a CI/CD pipeline configured in Azure DevOps or GitHub Actions. Pipelines automate build, test, security scanning, and deployment — reducing manual effort and ensuring consistent quality gates are enforced on every change without exception.

All pipelines must include the following stages in order:

Stage What it does Required?
Build Compile code, resolve dependencies, produce build artefacts Yes — all projects
Unit test Run unit tests and enforce the 80% coverage threshold Yes — all projects
Lint and format Check code style and formatting against project standards Yes — all projects
SAST scan Static application security testing on source code Yes — all projects
Dependency scan Check third-party libraries for known CVEs Yes — all projects
Integration test Run integration tests against containerised dependencies When applicable
Deploy to staging Deploy the build artefact to the staging environment Yes — on develop/main merge
DAST scan Dynamic security testing against the running staging application Yes — before every production release
E2E and accessibility test Run browser E2E tests and axe-core accessibility scan on staging Yes — before every production release
Deploy to production Deploy to production after manual approval gate is cleared Yes — with approval gate

Security scanning

Static application security testing (SAST)

SAST runs on every commit and analyses source code for security vulnerabilities without executing the application.

  • Approved tools: SonarCloud, Semgrep, GitHub Advanced Security (CodeQL)
  • Critical and high severity findings must be resolved before a merge to main is permitted
  • Medium and low severity findings must be tracked as tickets in the project's security backlog

Dynamic application security testing (DAST)

DAST runs against the deployed staging environment before every production release.

  • Approved tool: OWASP ZAP (automated scan configured in the CI pipeline)
  • All OWASP Top 10 findings at medium severity or higher must be resolved before a production deployment is permitted
  • DAST reports are uploaded to the project's security dashboard in Azure DevOps and retained for 12 months

Dependency and SCA scanning

Software Composition Analysis (SCA) checks third-party libraries against the National Vulnerability Database for known CVEs.

  • Approved tools: Dependabot (GitHub), npm audit, Snyk
  • Critical severity CVEs must be resolved within 5 business days of detection
  • High severity CVEs must be resolved within 15 business days
  • Medium and low severity CVEs are prioritised in the next regular sprint

Security findings are not optional

A pipeline with unresolved critical or high severity security findings will not advance past the SAST or DAST stage. There are no exceptions without a documented and approved risk acceptance from the CISO office.

Release management

Release gate checklist

A release cannot proceed to production until the release manager has confirmed all of the following:

  1. All CI pipeline stages have passed on the release branch with no bypasses
  2. SAST and DAST scans show no critical or high severity findings
  3. E2E tests pass on the staging environment against the build candidate
  4. Accessibility scan shows zero WCAG 2.1 AA violations on all primary user journeys
  5. A release note summarising changes, known risks, and rollback steps has been prepared and reviewed
  6. Change Advisory Board (CAB) approval has been received for standard changes to production
  7. On-call coverage is confirmed for the deployment window and for two hours following deployment

Approved deployment strategies

Teams must use one of the following approved strategies for all production releases:

  • Blue-green deployment — maintain two identical production environments; route traffic to the new version after validation. Preferred for stateless web applications and APIs.
  • Rolling deployment — gradually replace instances of the old version with the new version. Supported on Kubernetes and Azure Container Apps.
  • Feature flags — deploy code to production in a dormant state and enable features incrementally via a flag management tool. Recommended for large or high-risk changes.

Hotfixes to production follow an expedited process: a hotfix branch, peer review by at least one senior developer, a minimal pipeline run, and verbal CAB notification within one hour of deployment.
