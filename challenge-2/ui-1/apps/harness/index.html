Alberta.ca harness — how it works

How the harness turns a one-sentence brief into a Drupal-deployable prototype, and the checks that gate sign-off.

What the harness produces

The Alberta.ca harness turns a one-sentence brief into a working prototype — semantic HTML, plain CSS, vanilla JavaScript, no bundler — that is aligned to the Government of Alberta design system and ready to drop into Drupal for production. Each prototype lives in its own folder under apps/<slug>/ and is built by slot-filling a hand-curated canonical template. There is one source of truth for the chrome (header, footer, breadcrumb, sidebar nav) and one strict build path.

Required runtime assets

Four pieces must exist before build.mjs will produce a page. Three of them are committed to the repo as part of the harness; the fourth is generated per prototype.

PathWhat it isOwner
.claude/ Skill code, hooks, settings. Five progressive-disclosure skills under skills/. committed
CLAUDE.md Canonical entrypoint Claude reads first. Workflow, invariants, GoA class table, reset commands. committed
apps/_template/page.html Hand-curated master with {{SLOT}} placeholders for title, breadcrumbs, sidebar, body, and meta. Imports the 6 GoA stylesheets. committed
apps/_shared/vendor/css/ The 6 pre-split GoA stylesheets (goa-base, goa-layouts, goa-components × screen + print) sourced from the GoA core export. committed
apps/<slug>/ Per-prototype folder. Contains page.config.json, body.html, styles.css, app.js, requirements.md, and the generated index.html. per page

The 5 skills

Each skill is a folder under .claude/skills/ with a SKILL.md and any helper scripts. Skills are loaded progressively — Claude reads the description from the YAML frontmatter to decide whether to invoke a skill, then reads the body only when needed.

SkillPurposeWhen invoked
extracting-alberta-pages Refresh the vendored GoA stylesheets and canonical shell from upstream. First setup, after a GoA redesign, when prototypes look out of date.
generating-alberta-page Turn page.config.json + body.html into index.html by slot-filling the canonical template. Every new page or rebuild.
hosting-prototype Launch a local Node server. Single-app mode (serve.mjs in the app folder) or multi-app mode (serve-multi.mjs for whole programs). After building, when the user wants to click through the prototype.
evaluating-prototype Run 34 static checks against the built index.html — structure, design-system fidelity, JS hygiene, accessibility, responsiveness, and a requirements crosswalk. Sign-off gate. A prototype is not done until 0 FAIL.
writing-test-plan Generate a human-tester checklist as test-plan.md. Has single-page and multi-page-program templates. After the evaluator passes, before handing the prototype to a reviewer.

Single-page workflow

  1. Pick a kebab-slug for the prototype (e.g. report-red-tape, business-license-finder).
  2. Write apps/<slug>/requirements.md — bulleted, multi-word phrases so the evaluator crosswalk has signal.
  3. Write apps/<slug>/page.config.json by copying apps/_template/page.config.example.json and filling in title, lede, breadcrumbs, parent, and (if multi-page) sidebar.
  4. Write apps/<slug>/body.html as one or more <div class="goa-main-grid">…</div> blocks containing .paragraph.paragraph--type--text-block.goa-column-XX-XX-XX children.
  5. Write apps/<slug>/styles.css for page-namespaced rules only.
  6. Write apps/<slug>/app.js for page-namespaced behaviour (plain script, no ES imports, no globals).
  7. Run node .claude/skills/generating-alberta-page/scripts/build.mjs <slug>. Any unfilled {{TOKEN}} aborts the build.
  8. Copy serve.mjs into the app folder and launch on port 5179.
  9. Run node .claude/skills/evaluating-prototype/scripts/evaluate.mjs <slug> until it reports 0 FAIL.
  10. Write apps/<slug>/test-plan.md using the single-page template from the writing-test-plan skill.

Multi-page program workflow

A "program" is N single-pages that share a single sidebar configuration. The typical shape is one hub plus three topic pages plus an apply form. Real example: alberta-ip-office with five pages — Overview, IP Creation, IP Protection, IP Commercialization, Apply.

  1. Pick the program slug (e.g. alberta-ip-office) and the page set. Use the page-set sizing table in generating-alberta-page/SKILL.md if the brief does not match the canonical hub+3+apply shape.
  2. Compose one sidebar config block. The links list every page slug; the current: true flag will be flipped per page.
  3. Execute the single-page workflow once per page. Each page.config.json includes the same sidebar with current: true on its own slug.
  4. Launch serve-multi.mjs on port 5180. Every page is reachable at /<slug> with working cross-links.
  5. Evaluate every page. All must hit 0 FAIL.
  6. Write one program-level test-plan.md (in the hub app folder) using the multi-page template — includes chrome-consistency and cross-page-navigation sections.

The 34 evaluator checks

evaluate.mjs runs static analysis on the built index.html. Every check is either PASS (silent), WARN (should fix; may be waived with a written reason), or FAIL (blocks sign-off). A prototype is not declared done until every check is PASS or WAIVED-with-reason.

Sign-off rule

The harness treats 0 FAIL as the bar for “ready to hand off to the Web team.” Warnings are advisory but should be addressed or waived with a written reason in code.

Structure — 14 checks against the canonical template
  • S1 Has <!DOCTYPE html>
  • S2 <html lang="en"> set
  • S3 viewport meta present
  • S4 Single <h1>
  • S5 Has <main id="main" role="main">
  • S6 goa-skiplinks block before the header
  • S7 dialog-off-canvas-main-canvas wrapper
  • S8 <header> present
  • S9 goa-header block
  • S10 goa-logo with the SVG wordmark
  • S11 goa-breadcrumbs present
  • S12 goa-page-header block
  • S13 goa-footer block
  • S14 Heading order never skips (h1 → h2 → h3, never h1 → h3)
Design-system fidelity — 9 checks
  • D1 Imports goa-base.css
  • D2 Imports goa-layouts.css
  • D3 Imports goa-components.css
  • D4 Imports all 3 print stylesheets
  • D5 No live alberta.ca CSS bundle URLs (no sites/default/files/css/ in <link>)
  • D6 No legacy monolithic /_shared/vendor/alberta.css
  • D7 Forms use .goa-form and .goa-field (FAIL)
  • D7b Buttons use .goa-button (FAIL)
  • D7c No legacy .form-item / .form-required / .form-text (WARN)
  • D8 No utility-CSS framework imports (Tailwind / Bootstrap / Bulma / Foundation)
  • D9 All 6 vendored CSS files exist on disk
JS hygiene — 4 checks (anything that crashes the page)
  • J1 No orphan goa.init / ab.init / abComponents.init calls
  • J2 No Google Tag Manager scripts
  • J3 No drupal-settings JSON blob
  • J4 At most one <script src="./app.js"> tag
Accessibility heuristics — 4 checks
  • A1 Every <img> has alt
  • A2 Every form control has a <label for>
  • A3 Live region for form errors (aria-live)
  • A4 <noscript> fallback present when there is a form
Responsiveness — 1 check
  • R1 viewport sets initial-scale=1

Visual responsive behaviour at 320px / 768px / 1280px is verified by the human test plan, not the static evaluator. The vendored GoA CSS handles the breakpoints; the evaluator only verifies the meta tag is correctly set.

Requirements crosswalk

For each line in apps/<slug>/requirements.md, the evaluator extracts tokens of 4 or more characters and counts how many appear in the rendered HTML. If at least half match, the requirement is marked PASS; otherwise MISSING. The crosswalk produces a separate table in evaluation.md below the structural checks.

Write requirements as multi-word phrases that reference specific UI labels and field names. Single-word bullets trivially pass and give the crosswalker no real signal.

Submit API contract

Both servers expose POST /api/submit for form submissions. The endpoint accepts any JSON body and appends one NDJSON line to the appropriate submissions.ndjson file. The server adds received_at and, in multi-app mode, slug (derived from the Referer header).

Request

POST /api/submit
Content-Type: application/json

{ "any": "shape", "the": "form posts" }

Response (success)

HTTP 200
Content-Type: application/json

{ "ok": true, "id": "2026-05-12T05:14:51.257Z" }

Persisted NDJSON line

{"received_at":"2026-05-12T05:14:51.257Z","slug":"alberta-ip-office-apply","applicant_name":"Smoke Test","contact_email":"smoke@example.com","stage":"protection"}
  • received_at — always added by the server (UTC ISO timestamp). Also returned as the response id.
  • slug — added by the multi-app server only. Inferred from the Referer header. The single-app server omits it because the slug is implicit in the file path.
  • Everything else is verbatim from the request JSON body.
  • Bodies that fail to parse as JSON are still recorded as {"raw": "<text>"}.

Read back submissions via GET /api/submissions (single-app) or GET /api/submissions?slug=<slug> (multi-app). Returns the NDJSON file as text/plain.

Real GoA component classes

The vendored goa-components.css styles a specific vocabulary. Using generic Drupal classes (.form-item, .form-required, .description) or hand-rolled names (.btn, .card) yields unstyled browser defaults that look broken. Grep apps/_shared/vendor/css/goa-components.css before inventing a class.

<label for="x">Label</label> (required is default)inventing your own asterisk markup

Common gotchas

Callout variants are not optional

The bare <div class="goa-callout"> renders every child element at 24px / weight 700 / dark blue — a pull-quote treatment for single emphasis lines. Multi-line body callouts must use a variant (goa--important, goa--success, goa--error, goa--emergency, goa--event). If a proposed intro callout repeats the page-header lede, delete it — the lede is enough.

html_class only needs “js”

Older alberta.ca pages set classes like goa-stats-template and goa-loader-reset on the <html> element. Those are vestigial — nothing in the vendored CSS references them. The harness default is html_class: "js" and that is sufficient.

Forms must use goa-field, not form-item

Generic Drupal Forms API classes (.form-item, .form-required, .description) are not styled by goa-components.css. They render as browser defaults. Use <div class="goa-field"> for every input, <span class="optional">(optional)</span> for optional hints, and <div class="error-help"> for inline error messages.

No goa.init or ab.init

The real alberta.ca pages include inline scripts like goa.init(...) and ab.init(...) that reference a runtime JS bundle this harness does not ship. Including them in body.html causes a ReferenceError: goa is not defined on load. The static CSS is sufficient for prototype chrome; the runtime is only needed for off-canvas mobile menus, which prototypes do not use.

Theme assets are proxied

The favicon and other /themes/custom/goa_core/* assets are not vendored. Both servers proxy /themes/, /sites/, /system/files/, and /misc/ to www.alberta.ca so any missed asset reference returns 200 instead of 404. This proxy is bounded to those four path prefixes; everything else still 404s for genuinely missing files.

Drupal deployment

The harness output is structured to be paste-ready into Drupal Paragraphs. Each prototype maps to a Drupal node:

Prototype artifactDrupal home
page.config.json Drupal node fields — title, lede, breadcrumb parent, sidebar nav configuration.
body.html Pasted into Drupal Paragraphs (Text Block paragraph type). The .goa-main-grid + .paragraph.goa-column-XX-XX-XX structure mirrors how Drupal renders multi-column paragraphs.
styles.css Attached as a Drupal library (page-specific). Should remain small — bulk styling is provided by the live goa_core theme.
app.js Attached as a Drupal library (page-specific). The submit URL is rewritten from /api/submit to the production webform endpoint at deployment time.
header / footer / breadcrumb chrome Provided by the live goa_core Drupal theme. Not deployed.
vendored GoA CSS Already in production via the goa_core theme. Not deployed.

Reset to a clean slate

To start fresh while keeping the harness intact, delete every prototype folder under apps/ except _template/ and _shared/: 

ls apps | grep -v -E '^(_template|_shared)$' | xargs -I {} rm -rf apps/{}
rm -rf .claude/logs extractions

The harness will still build the next prototype on demand. apps/_template/ and apps/_shared/vendor/css/ remain because they are the runtime dependencies, not session output.

Sufficient on its own

After a clean slate, a fresh Claude session reading CLAUDE.md plus the five SKILL.md files has everything it needs to reproduce a working prototype from a one-sentence brief. The reference apps under apps/ are optional examples, not load-bearing documentation.
