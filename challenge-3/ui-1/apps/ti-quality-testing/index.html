Testing requirements overview

Automated testing is required for all TI-managed applications. Tests must be committed to the repository alongside the code they cover, and all test suites must pass before a merge to a protected branch is permitted.

Minimum coverage threshold

All new or modified code must maintain at least 80% unit test coverage on new lines. Projects below this threshold must have an approved remediation plan on file with the TI Quality team before the next sprint begins.

Types of testing

Unit testing

Unit tests verify individual functions, methods, or components in isolation. They are the foundation of any test suite and must be written by the developer as part of the definition of done for every story.

  • Test one logical behaviour per test case
  • Use mocks and stubs to isolate external dependencies (databases, APIs, file systems)
  • Tests must be deterministic — no reliance on external services, system time, or execution order
  • Name tests as behaviour specifications: "should return an error when the input is empty"

Integration testing

Integration tests verify that two or more components work correctly together. They are required when your application connects to a database, external API, or message queue.

  • Run against a local or containerised version of the dependency — never against production
  • Cover the happy path and at least one error scenario per integration point
  • Integration tests may run in a separate CI stage and are permitted longer timeouts than unit tests

End-to-end (E2E) testing

E2E tests simulate real user journeys through the application via a browser or API client. They are required for all public-facing web applications and critical internal business workflows.

  • Cover all primary user journeys identified in the project requirements
  • Include at least one negative path (invalid input, authentication failure, network error)
  • E2E tests run in CI against the staging environment before every production deployment

Accessibility testing

All web applications serving GoA employees or the public must meet WCAG 2.1 Level AA. Accessibility testing is required at two levels on every release:

  • Automated — run axe-core or an equivalent tool in your E2E suite on every page in the primary user journey
  • Manual — keyboard navigation check, screen reader test (NVDA + Firefox), and colour contrast review before each release to production

Accessibility is a release gate

Accessibility failures are treated as critical defects. A release cannot proceed to production if any WCAG 2.1 AA violations are present in the primary user journey.

Test-driven development (TDD)

TDD is recommended for all new feature development and required for bug fixes. Writing the failing test first clarifies acceptance criteria and ensures the fix is verified before the PR is raised.

The TDD cycle:

  1. Red — write a failing test that describes the expected behaviour
  2. Green — write the minimum code needed to make the test pass
  3. Refactor — clean up the implementation without breaking the test

Approved testing frameworks

Language / platform Unit and integration E2E and browser
JavaScript / TypeScript Jest, Vitest Playwright, Cypress
React / Angular Testing Library + Jest Playwright
Python pytest Playwright (Python)
.NET / C# xUnit, NUnit Playwright (.NET)
Java JUnit 5, Mockito Selenium, Playwright
Accessibility axe-core axe-playwright, axe-cypress

Unapproved frameworks require a written justification and sign-off from the TI Quality team before they are used in a GoA project.

CI pipeline test gates

The following checks must all pass before a merge to develop or main is permitted:

  • All unit tests pass with no failures or skips
  • Code coverage threshold (80% on new lines) is met and the coverage report is published
  • Integration tests pass (if applicable to the project)
  • No new accessibility violations from the automated axe-core scan
  • Linting and code formatting checks pass without errors
