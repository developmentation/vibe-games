GoA coding standards

All TI development teams must follow these coding standards for Government of Alberta projects. Standards apply regardless of the programming language or platform unless a language-specific exception is documented in your project's architecture decision record (ADR).

General principles

  • Write code for the next developer, not just the compiler
  • Prefer readability over cleverness — optimise for understanding, not brevity
  • Follow the principle of least surprise: code should do exactly what its name implies
  • Keep functions and methods small and single-purpose (aim for under 30 lines)
  • Do not commit commented-out code; use version control history instead

Naming conventions

Element Convention Example
Variables & functions camelCase (JS/TS), snake_case (Python) getUserProfile, get_user_profile
Classes & types PascalCase UserProfileService
Constants UPPER_SNAKE_CASE MAX_RETRY_COUNT
Files (JS/TS) kebab-case user-profile.service.ts
Database tables & columns snake_case user_profile, created_at

Branching strategy

All GoA repositories use a simplified GitFlow branching model. Deviations must be documented in the project's README and approved by the technical lead.

  • main — production-ready code. Protected. Merges only via an approved pull request.
  • develop — integration branch for in-progress features. Protected. CI runs on every push.
  • feature/<ticket-id>-short-description — individual feature work. Branch from develop; merge back to develop via pull request.
  • hotfix/<ticket-id>-short-description — emergency production fixes. Branch from main; merge to both main and develop.
  • release/<version> — release preparation. Branch from develop when a release is imminent; used for final testing and version bumps.

Branch protection rules

Direct pushes to main and develop are blocked on all GoA repositories. All merges require at least one approved reviewer and passing CI checks before the merge button is available.

Pull request checklist

Before submitting a pull request for review, the author must confirm all of the following:

  1. Code compiles and all existing tests pass locally
  2. New or changed functionality has corresponding unit tests with at least 80% coverage on new lines
  3. No secrets, credentials, or environment-specific values are committed (use .env files and a secrets manager)
  4. Code follows GoA naming conventions and the style guide for the language
  5. Public functions, classes, and API endpoints have descriptive documentation comments
  6. The PR description explains what changed, why it changed, and links to the relevant ticket
  7. Security-sensitive changes have been flagged and a security review has been requested if required
  8. Accessibility requirements have been considered for any user-facing changes

Code review process

Code review is a mandatory step for all merges to protected branches. Reviewers are responsible for:

  • Confirming the PR checklist has been completed by the author
  • Checking for logic errors, edge cases, and potential security vulnerabilities
  • Evaluating whether the approach aligns with the project's architecture and accepted patterns
  • Ensuring the code is readable, well-named, and appropriately documented
  • Providing constructive, specific feedback — avoiding general style preferences not covered by the linter

Turnaround expectation

Reviewers should complete reviews within one business day for routine pull requests. For time-sensitive hotfixes, contact the reviewer directly to request an expedited review.

Documentation requirements

Every GoA project repository must include the following documentation at all times:

  • README.md — project overview, local setup steps, required environment variables, and a link to the architecture diagram
  • CONTRIBUTING.md — how to contribute, coding standards reference, and the pull request process
  • CHANGELOG.md — version history following Keep a Changelog format
  • Architecture decision records (ADRs) — stored in docs/adr/, one Markdown file per significant decision
  • API documentation — OpenAPI 3.x spec for all HTTP APIs, generated and published to the GoA API catalogue

Inline code comments should explain why, not what. Well-named identifiers already convey what the code does.
